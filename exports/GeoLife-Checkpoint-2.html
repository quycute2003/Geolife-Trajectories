Image Lambda đã được thử trong emulator và đẩy lên ECR. Tạo Lambda trên AWS gặp HTTP 403. Nhóm chuyển sang Docker Desktop để tiếp tục triển khai và thử luồng. Trên Google Cloud, GKE là Google Kubernetes Engine. Cài Knative và Kourier trên GKE rồi tạo lại hai Revision. Cloud Load Balancing và HTTPS phục vụ lối vào public. API suy luận có thể để trong cụm, cho backend đặt xe gọi nội bộ qua Kourier. Đẩy image lên GHCR ở chế độ private. Kubernetes kéo image qua imagePullSecrets. Nạp snapshot GeoLife vào Cloud SQL for PostgreSQL. Hai Revision dùng chung DB và lấy cấu hình kết nối từ Kubernetes Secret.

Phục vụ API trên Kubernetes

Knative Serving và Kourier là gì?

Knative Serving

Công cụ chạy và quản lý dịch vụ web trên Kubernetes.

  • Tăng giảm số pod theo lượng request, có thể về 0 khi rảnh.
  • Giữ hai phiên bản và đặt tỷ lệ chia request.

Kourier

Cổng nhận request HTTP cho dịch vụ chạy bằng Knative.

  • Nhận request từ app đặt xe qua một URL.
  • Chuyển request vào Blue hoặc Green theo tỷ lệ đã đặt.
Kubernetes chạy pod chứa API. Knative gọi mỗi phiên bản triển khai là một Revision. Route giữ URL và tỷ lệ gửi request vào từng Revision. Kourier dùng Envoy để nhận và chuyển request theo Route. Khi một Revision đang có 0 pod, Knative khởi động pod khi có request. Demo local truy cập Kourier bằng kubectl port-forward.

Kiến trúc demo

Một API gợi ý, hai phiên bản dùng chung PostgreSQL

App gửi user_id qua Kourier và nhận lại Nhà, Công ty, POI cùng phiên bản model. Nét đứt biểu thị Knative Route cung cấp cấu hình định tuyến cho Kourier. Blue và Green dùng cùng image API và cấu hình baseline-v1. Cả hai đọc snapshot geolife-1.3-full-v1 từ PostgreSQL qua Kubernetes Secret. Script đăng ký lưu hai gói thuật toán vào MLflow để đối chiếu khi phát hành. Gói MLflow hiện dùng snapshot SQLite demo. Request API chạy bằng image đã triển khai.

Luồng API

API dùng GPS trực tiếp khi lịch sử có tối đa 100.000 điểm

POST /v2/locations/infer

{"user_id":"101"}

Trả Nhà, Công ty, POI cùng phiên bản model và snapshot.

128 người dùngTối đa 100.000 điểmĐọc GPS từ PostgreSQL rồi suy luận theo request.
54 người dùngTrên 100.000 điểmĐọc kết quả đã tính từ GPS đầy đủ theo model và snapshot.
User 101 có 13.738 điểm nên suy luận theo request. User 153 có 2.156.994 điểm nên dùng kết quả tính trước. Response có model_version, pipeline_version, config_version, config_sha256 và data_snapshot_id. Vai trò thiếu bằng chứng có trạng thái unknown. Bản tính trước dành cho lịch sử dài và được tạo từ toàn bộ GPS cho từng model. Nếu lịch sử vượt giới hạn thiếu kết quả tính trước, API trả history_too_large.

Tỷ lệ request Blue / Green

Blue/Green giữ bản cũ, canary cho Green nhận thử 10% traffic

Preview

100% / 0%Test Green qua URL riêng.
Canary90% / 10%Đo tỉ lệ, lỗi và latency.

Promote

0% / 100%Green nhận toàn bộ traffic.

Rollback

100% / 0%Đưa traffic về Blue.
Các tỷ lệ trên slide theo thứ tự Blue / Green trên cùng URL live. Blue/Green giữ hai Revision sẵn để kiểm tra hoặc chuyển về. Canary giới hạn phần traffic chuyển sang Green trước promote. Tỉ lệ quan sát dao động quanh trọng số. Các bước promote và rollback trong CP2 do người vận hành chạy.

Bước tiếp theo

Bước tiếp theo là đưa API lên cloud và đo lượt dùng gợi ý

Triển khai

Google Cloud

  • Đẩy image API lên GHCR.
  • Triển khai API trên GKE, kết nối Cloud SQL và cấu hình HTTPS.
Sản phẩm

A/B trên giao diện đặt xe

  • Cân bằng hồ sơ và nhiệm vụ giữa hai nhóm.
  • Đo tỷ lệ phiên xác nhận bằng gợi ý.
Canary dùng để theo dõi phát hành, còn A/B giữ nhóm theo người thử để đo hành vi. Chỉ tính phiên xác nhận bằng gợi ý khi người thử giữ nguyên điểm đến. Mẫu số chính là các phiên mở bước chọn điểm đến. Đo thêm tỉ lệ dùng gợi ý trong các phiên đã xác nhận và loại fixture khỏi số liệu người thử.
